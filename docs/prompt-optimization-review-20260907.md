# 工智寻优全流程输入与提示词优化审查

正式实例启动前，先验证本轮优化。实例必须通过系统的任务理解、MCTS/Fusion、报告三个实际子流程；可以分阶段执行，但不能用手工模型冒充系统结果。

## 已有流程的有效部分

- 任务理解已区分原始权威材料、数据画像、调查结论和模型推断；结构化评估合同与确定性渲染可减少任务书和机器上下文的口径漂移。
- AutoML 已采用固定任务前缀、追加式分步对话、失败反馈置后以及历史快照补读。MCTS 与融合的提示词保留同一评估协议、开发集隔离、OOF 对齐及最终测试集禁用规则。
- 报告已有节点资格筛选、评估口径可比性、融合来源与可复用接口分析；它能区分候选自报结果和独立复核证据。
- 服务和生成代码有内存限制与 CPU-only 配置；供应商 token、推理 token、本地响应缓存和供应商输入缓存分别统计。

## 成本证据与解释

历史小实例 796,970 输入 token、97,312 输出 token，输入占 89.1%。但供应商缓存字段只覆盖 7.65% 的输入，无法计算完整命中率。不能把缺失缓存信息当成零命中或已命中。

八条配送规则的表示对照为 866 → 391 输入 token，逐字保留全部规则；35 份 JSON 产物无损还原后的字符总量减少 42.7%。这些是表示与接口证据，不等于模型效果已经证明不下降。

钢厂旧流程的一次评估合同调用输入 16,383、缓存 16,128，输出 14,103（其中推理 10,876），耗时 560.59 秒。缓存已经较高，反复产生长篇规则推演仍然耗时且花费输出 token。本轮同时治理输入重复和不必要的修复轮次，保留用户指定的 `gpt-5.6-luna` 与 `xhigh`。

本轮 AutoML 消息构建器的两次真实接口测试都正确识别配送日期缺失、禁止假定日期、禁止宣称运营效果、无停靠点数量上限、软件检查指标和五个货主隔离。各请求输入 1,100 token；两次返回均缺失缓存字段，故命中率未知。不同长度与任务内容的调用不能直接拿来计算质量等价的节省比例。

官方文档 MCP 请求失败，官方缓存指南直连返回 Forbidden。第三方接口行为由实际返回与兼容性回归验证，不假定其缓存或定价完全等同于 OpenAI。

## 验证与验收

回归结果记录在运行目录 `optimization-validation/regression-results.json`，真实接口探测分别记录原始使用量、完整合同、报告及审查结果。机器清单 `prompt-inventory.json` 包含源码指纹、提示词长度、六项协议体积和验证结果。`optimization-review.json` 只有完成实际检查后才能置为 passed。

各任务理解阶段核对原始要求、关键字段、样本范围、缺口、泄漏、唯一指标与固定切分；AutoML 阶段核对实际三小时、有效候选与融合、独立复算、重新训练、模型加载和新输入推理；报告阶段核对每个效果数字的归属及比较口径，不把业务目标写成达到的效果。

六个正式实例各需 10,800 秒实际搜索。配送只交付模型与缺口报告。默认串行任务、每任务两个 Worker、单任务 8 GiB、整个服务树 10 GiB，资源压力停止后恢复已有搜索并排除停机时间。

正式实例启动前回归为 290 项通过、20 项跳过，覆盖完整 AutoRealize 和 AutoReport 测试、相关 AutoML/后端测试、阶段控制和用量去重；四个代码仓库的 `git diff --check` 均通过。流式截止除了模拟流，还通过本地真实 HTTP/SSE 与 SDK 套接字读取测试。跳过项不计为通过，真实供应商验证另行验收。

配送定向返修已正确将单候选有界软件评分与整次三小时搜索验收分开，并排除风险方案冒充确认服务。该次调用为 11,096 输入、13,513 输出（含 6,016 推理），248.72 秒；前一轮完整编译为 4,311 输入、32,002 输出（含 25,271 推理），580.06 秒。输入增多但输出和耗时减少，说明应根据明确缺陷修复已有合同；这不是同质量的完整 A/B，也不能直接推广为整体费用下降比例。

钢厂定向返修也通过独立内容检查：开发集用于调参与排名、训练区 OOF 拟合集成、最终留出隔离、算法选择开放、三小时运行与候选评分分离均已正确表达。实测 9,672 输入、8,960 缓存输入、13,890 输出（含 7,175 推理），415.12 秒；本次调用输入缓存命中约 92.6%，不能代表其它缺失缓存元数据的调用。详细接受与拒绝记录见 `optimization-validation/provider-review.json`。正式实例仍须逐阶段核验原始文件、全部约束和实际模型效果，探测通过不等于实例完成。

## 仍须实测的质量问题

- “完整保留输入”不能证明模型已经正确使用全部约束。逐任务独立验收仍是必要步骤。
- 大型文档的结构化抽取、代表性采样和补读是否覆盖关键业务例外，必须用原始材料核对。
- 报告完整上下文可能触及显式字符预算；先统计当前产物，再在真实窗口范围内调整预算或消除完全重复内容。
- 三小时搜索是否找到足够多可比候选、真正发生融合及改善、最终模型能否复用，尚不能由提示词测试回答。
- 供应商未提供缓存元数据的调用只能报告未知；未提供单价时不编造人民币费用。

真实无结果报告测试还发现了交付范围误读：把“只交付模型与缺口报告”当成可以只写设计，并把补日期作为开发求解器的前提。已补充模型仍须交付可运行代码与软件验证、日期只限制真实运营验收的指令。第二次真实报告已正确区分这些状态、保持五货主隔离和无停靠点上限、不编造候选与收益。审查后报告 3,862 字符，首份 9,823 字符；但总 API 输出 token 没有随正文等比例下降，不能声称降低了总费用。

两轮实际报告的六次调用共返回 46,640 输入 token 和 60,208 输出 token，缓存元数据覆盖 76.16% 的输入；全量命中率未知，已观测命中下限为 29.09%。这些数字不包含没有返回 usage 的失败合同请求，也不包含单独的两次 AutoML 消息路由探测。报告输出与推理消耗同样需要持续优化。
