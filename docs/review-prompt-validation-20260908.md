# 审查 Prompt 优化与真实 API 对照

本次验证聚焦任务定义中的产物一致性审查、评估合同审查及最终定稿。最终启用产物审查和合同定稿的新编排；普通评估审查保留旧编排，因为新版仍出现质量退步。使用逐门架车流任务的冻结产物，以及带已知答案的车流/配送约束测试。请求发送到用户指定的 Renice，模型参数为 `gpt-5.6-luna`，推理强度 `xhigh`，输出上限始终为 `32768`。所有运行实例和训练产物均未被本次实验修改。

## 已实现的编排

旧编排已经支持精确重复 JSON 值引用。本次在其基础上合并原先分散在多个消息中的权威背景、当前证据与完整待审产物，扩展跨对象去重，消除仅字典键顺序不同造成的重复，并对长 Markdown 中完全相同的行进行可还原引用。

| 位置 | 内容 | 变更方式 |
| --- | --- | --- |
| 固定前缀 | 原始需求、权威来源与任务约束 | 保留完整传入内容 |
| 当前快照 | 当前阶段证据、完整合同、完整描述及其镜像 | 只引用完全相同的值；不同值分别保留 |
| 审查要求 | 角色要求、JSON schema、一致性检查 | 按角色固定 |
| 动态末尾 | 本轮指令、轮次、具体缺陷及返修反馈 | 追加最新控制信息 |

编码后的完整快照会在发送前由程序解码，并与编码前的所有值比较。换行、缩进、数字类型、空值、冲突值和源文本中已有的引用标记都有回归覆盖；还原不一致时拒绝发送。完整审查快照不再触发历史草稿的付费摘要和检索调用。这里的完整性范围是实际传入审查阶段的权威背景、阶段证据及当前产物，不代表重新读取了所有原始数据行。

缓存只可能复用相同前缀。只改反馈时快照字节保持一致；若修复了合同或描述，变化位置之后的前缀不能继续按旧内容复用。本次没有向 Renice 强行添加未经确认支持的缓存参数，也没有将模型名称改写成另一模型。

## 质量比较

第一版仅调整编码的新版审查，在冲突样本中发现了全部四项注入错误，却漏掉旧版发现的两项真实问题。因此该版本未启用。最终审查增加八个明确维度：任务与时间语义、人口算术、主指标与方向、输出键与列、物理 schema 与文档角色、因果性与留出集、权威及未解决事项、产物镜像一致性。每项必须说明证据与推导。

逐项人工复核了真实 API 返回的缺陷及修复建议，比较依据是具体问题，而不是简单比较 `issues` 条数：

| 检查项 | 最终新版结果 |
| --- | --- |
| 将 MAE 方向注入为 maximize | 检出，要求恢复 minimize |
| 注入 invented_prediction_column | 检出，恢复真实四列输出合同 |
| 允许第七日标签选择模型及融合权重 | 检出，明确禁止留出泄漏 |
| 无证据宣称 60 分钟口径已获正式裁决 | 检出，保留并列口径及真实缺口 |
| 共同预测起点数量的端点错误 | 检出并推导：一天 277 个、五天 1429 个，单日双跨度 554×门架数 |
| 独立跨度并集与共同起点输出规则冲突 | 检出，对比 560×门架数和 554×门架数 |
| 预测起点被解释为最后观测时间 | 在真实未注入样本中检出，定位到 ml_dl.target |
| 文档术语被标为 physical_schema | 检出，区分 PDF/DOCX 需求文档与真实表列 |
| 工作簿读取示例缺少已核验 Sheet 参数 | 在真实样本中检出，保留精确 Sheet/字段 |
| 当前执行合同仍列出已由后续证据解决的旧疑问 | 在真实样本中检出；要求保留仍未解决的业务问题 |

真实样本旧版报告 4 项、新版报告 6 项；注入冲突样本旧版和最终新版均报告 7 项，问题的合并方式有所不同。最终新版覆盖旧版主要发现，补回了第一次优化漏掉的端点与文档角色问题。单次 LLM 输出仍有波动，这不是全任务召回率或模型效果不变的统计证明。

受控测试中，旧版和最终新版均放行正确样本，均拒绝全部四项已知错误：留出泄漏、伪造口径裁决、填充缺失运力日期、凭空增加每车 5 站上限。六次独立约束保留调用均逐字返回全部 C01-C12，包括不可混装货主、重量/体积双容量、不能假定配送日期、独立训练/推理交付及 GPU 证据要求。

评估合同另做逐句比较。第一版新版虽通过结构检查并保留九项未解决事项，但 `computation_scope` 一处将主指标一并列入“仅审计指标”。该表述被判定需要修复。随后补充了主指标、公式、计算范围、审计指标、评估人口与分区之间的交叉核对要求，并对正常审查及最后一轮定稿重新进行真实 API 验证。

补测结果：新版最后一轮定稿正确给出 277/1429 个起点和 554×门架数，主排序与审计用途清楚分开，全部九项未解决事项、留出隔离、真实字段和交付要求保留；旧版定稿同样正确。普通评估审查新版修复了指标用途措辞，却再次照抄 276/1428/552 的错误计数，因此没有启用这一分支。程序结构检查对这些语义错误仍返回无缺陷，说明不能用 JSON 合法或字段齐全代替质量验收。

## 输入与缓存实测

下面是 provider 返回的输入 tokens，包含最终审查新增的覆盖检查开销：

| 场景 | 旧版输入 | 最终新版输入 | 输入变化 |
| --- | ---: | ---: | ---: |
| 真实车流产物一致性审查 | 119161 | 102564 | -13.93% |
| 注入四项冲突的完整审查 | 122134 | 103982 | -14.86% |
| 最后一轮评估合同定稿 | 56659 | 50555 | -10.77% |
| 正确受控样本 | 3782 | 3828 | +1.22% |
| 冲突受控样本 | 3608 | 4123 | +14.27% |

对于小输入，八维检查会增加输入和输出开销；例如正确受控样本新版输出 3812 tokens、旧版 194 tokens，均包含推理。不能声称每次调用都更便宜或更快。实际大样本审查的输出为旧版 15004、新版 14170；注入冲突审查为旧版 11855、新版 11564。

同证据、仅改变末尾反馈的重复请求中，实际缓存计数如下：

| 第二次请求 | 总输入 | 缓存命中 | 未缓存输入 | 命中比例 |
| --- | ---: | ---: | ---: | ---: |
| 旧版 | 2583 | 1792 | 791 | 69.38% |
| 新版 | 2087 | 1792 | 295 | 85.86% |

两者命中 tokens 相同，新版主要减少了未缓存输入，降幅为 62.71%。新版第一次请求也返回了 1792 命中 tokens，但之前已执行相似受控用例，因此不能把它视为严格冷启动。大样本的新请求没有返回缓存明细，其缓存状态仍为未知，不能按零命中统计。

未启用的普通评估审查实验：旧版 56318 tokens，第一版新版 50074，补测新版 50232。虽然输入减少，但质量门禁未通过，这部分节省不计入发布收益。

这些数据支持“减少重复输入并保持可复用前缀”，不能外推为全流程命中率提升、人民币费用下降比例或固定加速倍数。旧版和新版都遇到过 524 代理超时；耗时包含网络重试，未返回 usage 的失败尝试也可能产生无法统计的费用。

## 证据与复现

所有对照都使用相同的源文件哈希和完整冻结证据，结果目录内包含 `snapshot.json`、实际请求 `request.json`、返回 `result.json` 以及 usage。未存入 API 密钥。汇总脚本会校验完整冻结载荷，包括权威背景，并保存请求/结果哈希。语义质量结论来自上述逐项复核，程序门禁不能替代它。

- `runs/industrial-examples-20260907/optimization-validation/review-ab-v2`：旧版基线及被退回的第一版优化。
- `review-ab-v3`：最终产物审查，含八维覆盖证据。
- `review-controlled-v1`：受控旧版基线及约束保留。
- `review-cache-v3`：顺序重复请求的真实缓存遥测。
- `review-evaluation-v4`：补充一致性要求后的评估合同审查。
- `review-finalizer-v4`：最后一轮合同定稿的旧/新对照。
- `review-release-final`：发布代码离线重建的请求和 schema；启用分支与对应真实 API 测试逐值一致，普通评估审查的 old/new 请求完全相同。
- `review-comparison-20260908.json`：由下面的汇总命令生成，包含完成/失败状态、配对数据、门禁及证据哈希。

```powershell
python scripts/summarize-review-validation.py --root runs/industrial-examples-20260907/optimization-validation
python -m pytest core/AutoRealize/tests -q
```

API 响应中的 `model` 多次显示 `gpt-5.6-terra`，而请求指定 `gpt-5.6-luna`。未擅自换模型，也无法独立核实服务商内部路由；因此这里是该 Renice 端点实际返回结果的对照，不能称为已验证原生 luna 的行为。

## 发布状态

`prompt.lossless_review_prompts` 已设为默认启用，范围限于通过逐项质量复核的最终产物审查和评估合同最终定稿。普通评估审查仍使用旧编排。显式设置为 `false` 可让这两个阶段也使用旧编排。既有进程和任务配置未被重启或覆盖；后续新进程加载默认配置时生效。

本次列出的实验共 23 个调用结果：22 个完成、1 个因多次 524 超时失败，不包含底层网络重试次数。完整本地回归为 **261 passed, 20 skipped**；本次新增测试覆盖编码逐值还原、动态反馈前缀稳定、完整快照不调用历史摘要/检索、八维审查结构、矛盾判定不能通过、输出上限，以及未通过版本不能进入普通评估审查分支。

长期仍应减少约束在任务书、机器合同和历史状态中的反复改写，并区分已解决疑问和当前业务缺口。当前剩余约十万 tokens 包含很多不完全相同的文本，本次保留这些差异以便审查发现矛盾，未用摘要或截断强行追求更大降幅。本轮结果不代表已经重新验证 AutoML 三小时搜索的模型质量或报告全流程成本。
